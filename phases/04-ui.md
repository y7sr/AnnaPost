# Phase 4 — UI (Admin Dashboard)

Not present in `plan.annapost.md` — the original plan is API-only ("External systems should mostly interact with the database through the API", section 2). This phase adds an operator-facing admin UI on top of the same API/services. It is an explicit, reviewed scope addition, not something implied by the original document.

## Goal

A small internal dashboard for day-to-day operation — creating/scheduling posts, watching jobs and events, reading metrics, moderating comments — without needing the CLI or raw API calls. It must **not** become a second integration boundary: the UI calls the same services/repositories the API uses, and `/api/v1` remains the contract external producers (Vend1r etc.) depend on (section 2, 21).

## Tech choice

Kept consistent with the project's stated minimalism (section 1: "do not introduce unless clearly necessary", "remain simple enough to run locally or on a small server"):

- **Server-rendered HTML** via Jinja2 templates, served by the existing FastAPI app under a distinct `/admin` prefix — no separate frontend service, no Node build pipeline
- **HTMX** (via CDN or vendored single file, no bundler) for partial-page updates: polling job/post status, inline actions — instead of a React/Vue SPA
- Minimal hand-written CSS, no CSS framework
- Metrics charts: server-rendered SVG sparklines, or Chart.js via CDN if interactivity is worth it — decide when task 5 is implemented, don't add a charting library speculatively
- New dependencies beyond section 1's list: `jinja2`, `python-multipart` (HTML form posts). Nothing else.

## Pages

### 1. Accounts
List all accounts; edit name/enabled; set default (enforces the single-default invariant via the same service as the API); show `last_successful_api_call_at`/`last_error_at`/`last_error`. Never render `access_token_ref` value (section 31).

### 2. Posts
List with status filter (draft/ready/scheduled/publishing/published/failed/delete_requested/deleted/canceled); detail view showing state, `publish_attempt_count`, Instagram IDs, permalink, `last_error`; create form (image first, per section 23's priority order); manual actions — publish now, cancel, soft-delete — all going through `services/posts.py`, never a direct status write from the route handler.

### 3. Jobs
List with type/status filter; `run_after`/`attempts`/`last_error` visible; retry/cancel actions call the same job-repository functions the runners use.

### 4. Events
Read-only timeline per account/post — a view onto the append-only `instagram_events` log (section 15). No write actions on this page.

### 5. Metrics
Per-post snapshot history with a simple chart (views/reach/likes over time). NULL is rendered as an explicit "—", zero is rendered as "0" — never conflate the two (section 12, 34).

### 6. Comments
Inbox of incoming comments; outgoing queue with status (`pending`/`sent`/`failed`); reply form that creates a local row + `reply_comment` job (section 14) — no synchronous Instagram call from the UI route handler.

## Cross-cutting

- **Auth**: none for v1, consistent with section 31 ("trusted/local deployment, do not overengineer auth"). Admin routes live under a distinct `/admin` prefix specifically so auth can be added later without touching `/api/v1`.
- All UI route handlers call existing `services/*`/`repositories/*` — zero duplicated business logic, zero direct DB writes from `api/routes` or the new `admin/routes`.
- No secrets/tokens ever rendered into a template (section 31).

## Deliverables
- `/admin` routes + Jinja2 templates for all six pages above
- Static assets (CSS, htmx) served by FastAPI's static file handling
- Smoke tests (`tests/api` or a new `tests/ui`) asserting each page renders 200 with expected key content

## Definition of Done
An operator can, using only the browser (no CLI, no raw API calls): view accounts, create/schedule/publish/soft-delete a post, watch job status change, read the event timeline, see metric history with correct NULL-vs-0 rendering, and send a comment reply.
